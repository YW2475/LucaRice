# Agent Note：DeepPlant 账户与工具隔离

状态：已实现

[English](2026-09-08-deepplant-account-and-tool-isolation.md) | 中文

## 问题

DeepPlant 的账户服务原来由田块管理宿主创建。加载该业务插件失败时，登录能力可能与田块访问一起消失。Agent 与设置页面也可能同时更新田块记录；RAG 宿主还会等待模型就绪后才允许 Web 应用完成启动。

这些耦合不适合小规模公网灰度测试：可选业务服务故障时，身份系统仍应可用；两个正常写入也不应互相覆盖。

## 决策

- 将账户服务注册为独立的 Web 应用插件。
- 登录会话、各账户的模型凭据、田块记录和导出文件继续关联到当前登录账户；知识包和本地推理模型保持只读共享。
- 停用普通账户后拒绝该账户登录，并使其已有会话失效。管理员可以创建用户、重置密码、启用或停用普通账户，并查看五个本地业务服务是否可用。
- 使用一个进程内锁串行化田块记录的读取—修改—写入，使 Agent 更新与设置页面更新经过同一持久化路径。
- RAG 模型加载时不再阻塞 Web 启动。RAG、确定性工具、语音、田块管理和天气继续作为彼此独立的进程，并分别提供就绪状态。

## 考虑过的替代方案

- 本阶段不把全部账户和田块数据迁移到新数据库。计划中的单服务器 50–100 人灰度测试只需要一个账户进程和一个田块服务进程。只有在 DeepPlant 需要多服务器实例，或业务记录需要关系查询时，才迁移数据库。
- 不把全部 Python 工具合并到一个进程，因为一个工具故障会同时移除无关能力。
- 不让 Web 进程继续等待 RAG 就绪，因为模型加载或暂时不可用时，用户仍应能够登录并使用未受影响的功能。

## 结果

单个本地工具不可用时，Web 应用仍能启动并保留登录。管理员可以看到需要处理的服务；停用账户会立即使该用户的活动会话失效；同一田块服务进程内的写入不再竞争。

这并不代表应用已经支持多节点部署。账户 JSON 与田块 JSON 仍分别由单一进程管理，RAG 推理也仍由当前模型服务串行执行。以后增加到多个应用服务器之前，需要把账户、会话和可变业务记录迁移到共享数据库，并按目标硬件完成并发测试。
